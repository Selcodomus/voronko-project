**Завдання 3**  
**1\. «Система має бути швидкою»**  
Порушені критерії якості: неоднозначність, неперевірність (немає критеріїв швидкості).  
Виправлений варіант: час відгуку системи на будь-яку дію користувача (пошук, перехід між сторінками) не повинен перевищувати 1.5 секунди при стабільному інтернет-з'єднанні.  
**2\. «Інтерфейс повинен бути зручним і сучасним»**  
Порушені критерії якості: неоднозначність (поняття "зручний" і "сучасний" суб'єктивні), неперевірність.  
Виправлений варіант: користувач повинен мати можливість знайти локальну подію та перейти до екрана оплати квитка, зробивши не більше ніж 3 кліки з головної сторінки платформи.  
**3\. «Система повинна підтримувати багато користувачів»**  
Порушені критерії якості: відсутність повноти та конкретики (скільки саме "багато"?).  
Виправлений варіант: серверна частина системи повинна успішно обслуговувати до 10000 активних сесій користувачів одночасно без втрати даних та критичних збоїв.  
**4\. «Видача оформлюється, і штраф нараховується, і формується звіт»**  
Порушені критерії якості: неатомарність (одна вимога містить три різні бізнес-процеси).  
Виправлений варіант:

1. Система повинна дозволяти адміністратору оформлювати видачу квитка.  
2. Система повинна автоматично нараховувати комісію за скасування події організатором.  
3. Система повинна генерувати фінансовий звіт для організатора за вказаний період.

**Завдання 6**  
Набір створених вимог перевірив за такими критеріями:

* Однозначність: усі вимоги мають єдине тлумачення.  
* Повнота: MVP покриває весь базовий флоу користувача (від реєстрації до сканування квитка).  
* Перевірність: для кожної NFR задано кількісний показник та інструмент вимірювання.  
* Несуперечливість: вимоги не конфліктують між собою.  
* Атомарність: кожна вимога описує лише одну функцію або властивість.

**Індивідуальне завдання**  
**1\. Продуктивність (NFR-01: Завантаження сторінки до 2 сек)**  
**Спосіб вимірювання:**

* **Інструмент:** Google Chrome Lighthouse (вкладка Performance) та метрика LCP (Largest Contentful Paint).  
* **Сценарій:** користувач з мобільного телефону (мережі 4G/LTE) заходить на головну сторінку, де завантажується стрічка з 20 афіш подій.  
* **Порогове значення:** LCP \< 2.5 с, Time to Interactive (TTI) \< 2 с.

**Наслідки для архітектури:**

* Необхідність використання CDN (Content Delivery Network) для швидкої віддачі зображень (афіш подій).  
* Впровадження пагінації (або "нескінченного скролу") — дані з бекенду мають віддаватися порціями (по 10-20 подій), а не всі одразу.  
* Використання кешування (наприклад, Redis) для частих запитів (список популярних подій у Луцьку), щоб не навантажувати основну базу даних.

**2\. Безпека та Надійність (NFR-04: Робота з платіжними даними без їх збереження)**  
**Спосіб вимірювання:**

* **Інструмент:** OWASP ZAP для перевірки вразливостей (Security Testing) та аудит коду.  
* **Сценарій:** користувач вводить дані картки на екрані оплати; перехоплення мережевого трафіку показує, куди йдуть дані.  
* **Порогове значення:** 0 записів з номерами карток чи CVV у логах сервера та базі даних EventTicket.

**Наслідки для архітектури:**

* Система не матиме власного модуля процесингу карток. Архітектура повинна включати інтеграцію з надійним платіжним провайдером (наприклад, LiqPay, WayForPay чи Stripe) через API.  
* Використання токенізації: бекенд платформи зберігатиме лише токени транзакцій та статус платежу, а всі чутливі дані вводитимуться у захищеному віджеті на стороні клієнта (iframe платіжної системи).  
* Вимога переходу виключно на протокол HTTPS для всіх з'єднань платформи.
